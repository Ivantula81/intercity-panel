# Справочник расписаний

Миграция `schema28.sql` добавляет проверенное расписание отдельно от прежнего десятиминутного кеша GDS. Перед применением на сервере сделать проверяемую резервную копию и выполнить миграцию целиком; частичное применение не поддерживается.

Ключ расписания — нормализованное название маршрута и плановое время отправления начальной станции (`HH:MM`). Направление и другое время старта образуют отдельную запись. Время остановки хранится как локальное `HH:MM` плюс день относительно даты выезда (`0` — день выезда, `1` — следующий день).

Первый импорт сохраняет исходные значения ведомости в `manifest_schedule_state.source_json`. Нажатие «Проверить обновления ГДС» только добавляет предложения на экран. Пользователь явно выбирает значения, отмечает расписание проверенным и сохраняет его. Уже подготовленная ведомость получает снимок применённой версии; будущие ведомости используют новую версию после импорта.

Если ГДС не отвечает, данные не перезаписываются. Остановка сопоставляется сначала по ID; связывание по названию возможно только явным действием оператора. Разовая правка времени в уведомлениях записывается в `overrides_json` и действует для всех направлений с этой станции только в текущей ведомости.

Проверки:

```text
php tests/route_schedule_test.php
./scripts/preflight.sh
```

Локальный экран без продовой БД, ГДС и рассылок можно открыть так:

```text
SCHEDULE_TEST_DB=/private/tmp/route-schedule-ui.sqlite php -S 127.0.0.1:8137 tests/route_schedule_fixture.php
SCHEDULE_TEST_URL=http://127.0.0.1:8137 node tests/route_schedule_ui_test.cjs
```

Тестовый сервер намеренно не содержит отправки сообщений и внешнего запроса ГДС.

## Выпуск и откат

До выпуска сверить commit `main` с `/root/panel-src` и хеши файлов с `/var/www/panel`, сохранить полный дамп базы и проверить восстановление в отдельную временную БД на сервере. Не копировать персональные данные в локальные тесты или репозиторий.

Preflight миграции: новые таблицы `verified_route_schedules`, `manifest_schedule_state`, `route_schedule_events` отсутствуют либо их определения полностью совпадают с schema28. Миграция добавляет только эти таблицы; старый кеш `route_schedule` не меняется. Применить schema28 целиком перед переключением кода. Повторное применение безопасно; оно не заменяет существующие строки. Старые миграции повторно не применять.

В отдельной пустой MariaDB проверить schema28 и тесты сервиса через `SCHEDULE_TEST_DSN=mysql:dbname=panel_schedule_test_<суффикс>`. Тест разрешает только такое имя отдельной БД. Проверяются создание, повтор миграции, rollback транзакций, конфликт версий и отказ обязательного аудита. Полный дамп дополнительно восстановить в другую временную БД и сравнить число строк всех таблиц.

Откат приложения: вернуть зафиксированный предыдущий commit из main и выполнить штатный deploy. Новые таблицы сохранить — это позволяет не потерять уже введённые расписания и разовые правки. В старом интерфейсе эти поправки не видны; после возврата к новой версии они снова доступны. Не удалять новые таблицы и не восстанавливать старый полный дамп поверх активной БД, поскольку после выпуска могли появиться новые сообщения и ведомости.

## Проверка рисков

- RISK-001/013: выпуск только из main после проверки хешей и схемы; резервная копия и восстановление проверяются до релиза.
- RISK-002: сохранение справочника требует администратора; оператор может читать и применять проверенную версию к ведомости. Действия требуют POST и общей проверки CSRF.
- RISK-004: явное сохранение, ошибка сохраняет введённые поля; конфликт версии возвращает 409. UI проверяется с настоящим каркасом панели на desktop и 390 px.
- RISK-007: первичная привязка расписания входит в существующую транзакцию импорта; повторный импорт не меняет ранее подготовленную ведомость.
- RISK-008: неподтверждённое новое время нельзя передать прямо в отправку; сначала завершается сохранение. Тесты не вызывают провайдеров сообщений.
- RISK-012: сохранение и применение записывают автора и версию в обязательный журнал `route_schedule_events` в той же транзакции.

Apple Design: локальный skill и upstream GitHub сверены 11.09.2026 и совпали. Использованы системная типографика, спокойные поверхности, один основной блок сохранения, компактная пара времени/дня, мгновенная реакция кнопок, фокус клавиатуры и reduced motion. Оформление ограничено экраном расписания.

Продовые отправки в проверках не используются.
