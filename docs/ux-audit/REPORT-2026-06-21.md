# UX/UI и продуктовый аудит панели «Интерсити Тур»

Дата: 21 июня 2026  
Объект: `crm.terratranskrym.ru`, репозиторий `Ivantula81/intercity-panel`  
Статус: исследование и концепт; код боевой панели не менялся.

## Короткий вывод

Панель уже выглядит цельно и профессионально. Визуальную систему, фиолетовый акцент, карточки, пошаговую отправку и адаптивную основу нужно сохранить. Полный редизайн или миграция на тяжёлый SPA сейчас принесут больше риска, чем пользы.

Главное ограничение продукта — не дизайн, а модель операционной работы:

1. Входящие чаты собраны по номеру телефона, но не имеют очередей, статуса, ответственного, приоритета и явного канала.
2. «Ведомости», «Уведомления», «Контакты», «Чаты» и документы существуют как отдельные разделы, хотя для диспетчера это одна сущность — рейс и связанные с ним пассажиры/сообщения.
3. На мобильном экране мастер отправки перекрывается собственной sticky-панелью отправки и нижней навигацией.
4. Контакты, справочники и логи загружают большие объёмы редактируемого DOM сразу; это пока терпимо, но плохо масштабируется.
5. Несколько ручных технических действий («Проверить каналы», «Починить статусы») должны стать фоновыми системными процессами или диагностикой администратора.

Главная рекомендация: не переделывать всё. Сначала превратить «Чаты» в рабочий единый inbox, связать его с рейсом и упростить навигацию вокруг сценария «рейс → пассажиры → уведомления → ответы → закрытие вопросов».

## Как проводилась проверка

- Проверены все маршруты и шаблоны в коде, CSS/JS, API чатов и схема каналов.
- Выполнен авторизованный read-only проход по production. Никаких сообщений, изменений, удалений и тестовых отправок не делалось.
- Подтверждено, что production CSS и JS побайтово совпадают с текущим локальным репозиторием (SHA-256 одинаковы).
- На production на момент проверки: 65 диалогов, 2 диалога с непрочитанными, 3 непрочитанных сообщения; канал WhatsApp был в состоянии `open`.
- Production-данные не сохранены в репозиторий. Скриншоты ниже сделаны на точных текущих шаблонах и CSS с синтетическими данными, чтобы не публиковать ФИО, телефоны, документы и переписку пассажиров.

Ограничение: динамические состояния после отправки и реальные QR/вложения не активировались — аудит был намеренно без внешних побочных эффектов.

## Что уже хорошо и должно остаться

- Единая визуальная система: спокойный фон, ясные поверхности, стабильные радиусы, узнаваемый бренд.
- Чёткая четырёхшаговая модель уведомлений: ведомость → данные рейса → группы → отправка.
- Видимые статусы доставки и ошибок; подтверждение перед массовой отправкой.
- Хорошая карточка ведомости с inline-редактированием и быстрым переходом к документам/рассылке.
- Адаптивная нижняя навигация и отдельный полноэкранный режим чатов.
- Синтетически простая архитектура PHP: её можно развивать постепенно, без переписывания продукта.
- Канальная абстракция уже есть на сервере; это хорошая база для омниканального inbox.

## Приоритетные проблемы

### P0 — исправить до новых крупных функций

1. **Мобильная sticky-панель отправки перекрывает мастер.** На ширине 390 px блок шага 4 висит поверх «Данных рейса» и частично конкурирует с нижней навигацией. На мобильном его нужно либо сделать обычным блоком в потоке, либо поднимать над нижней панелью с корректным `bottom`, показывать только после готовности групп и сворачивать в компактную строку.

2. **Ошибки API часто не имеют общего UI.** Базовая функция `api()` без проверки HTTP-статуса и без `try/catch` сразу вызывает `r.json()`. Потеря сети, HTML-ошибка PHP или истёкшая сессия могут оставить интерфейс в состоянии «Загрузка…». Нужны единый toast/error boundary, повтор действия и явная авторизация после 401/419.

3. **Канал сообщения теряется в UI чатов.** SQL выбирает `channel`, но API `chat.messages` не включает его в итоговый объект. В пузырях невозможно понять, через какой канал пришло/ушло конкретное сообщение.

4. **Опасные и второстепенные действия визуально близки.** «Очистить» и «Удалить ведомость» выглядят почти одинаково; удаление должно быть danger-действием в меню `…`, а «Очистить экран» — нейтральным действием.

### P1 — самый высокий продуктовый эффект

1. **Сделать из «Чатов» рабочий inbox**, а не только просмотр переписки.
2. **Связать разговор с рейсом/ведомостью** и показывать контекст пассажира справа.
3. **Перестроить навигацию по рабочим сценариям**, а не по внутренним таблицам системы.
4. **Сделать дашборд операционным:** ошибки, непрочитанные, ближайшие рейсы, незаполненные данные и недоставленные сообщения должны быть кликабельными задачами.

### P2 — масштабирование и качество

- Серверная пагинация контактов, логов и справочников.
- Очередь исходящих с идемпотентностью, ретраями и планированием.
- Фоновые проверки наличия каналов и их срока актуальности.
- Доступность с клавиатуры, контраст вторичного текста, корректные `aria-current`, focus-состояния и минимум 44×44 px для мобильных действий.
- Автотесты критических сценариев и статический анализ PHP.

## Как устроить входящие и разделение по каналам

### Не делать каналы отдельными мирами

Основная очередь должна отражать работу оператора:

- Новые;
- Мои;
- Без оператора;
- Ожидаем пассажира;
- Просроченные;
- Закрытые.

WhatsApp / MAX / Telegram / email должны быть фильтрами и цветными маркерами внутри этих очередей. Если сделать канал верхним уровнем, оператору придётся по очереди проверять вкладки и легко пропустить срочный ответ в «не той» вкладке.

Исключение: разные номера/бренды/юридические линии можно оформить как отдельные inbox-источники, но поверх них всё равно нужна общая рабочая очередь.

Это соответствует зрелому shared-inbox паттерну: Chatwoot прямо выделяет единую очередь, private notes, назначения и общий контекст; Front и Intercom также строят омниканальную работу вокруг единого inbox, а не отдельных окон мессенджеров ([Chatwoot Shared Inbox](https://www.chatwoot.com/features/shared-inbox), [Front Omnichannel Inbox](https://front.com/product/omnichannel-inbox), [Intercom Inbox](https://www.intercom.com/helpdesk/inbox)).

### Идентичность разговора

Сейчас ключом диалога фактически является телефон. Это удобно для контакта, но неверно для канальной истории. Разговор нужно идентифицировать минимум так:

`channel_account + external_chat_id + contact_id`

Телефон остаётся атрибутом контакта. Тогда сообщения одного пассажира в WhatsApp и MAX можно показывать в общей карточке контакта, но не смешивать их происхождение и reply-target.

### Минимальная модель данных

- `channel_accounts`: WhatsApp/MAX/TG/email аккаунты и служебные настройки.
- `conversations`: контакт, канал, внешний chat id, статус, приоритет, ответственный, связанный рейс, last message, unread, snooze.
- `conversation_messages`: направление, канал, provider id, тип, текст, media, delivery/read state, автор, timestamp.
- `conversation_events`: назначение, смена статуса, private note, merge/link.
- `outbox_jobs`: idempotency key, scheduled_at, attempts, next_retry_at, last_error.

Миграция должна быть добавочной: создать новые таблицы → backfill из `messages`/`inbox` → временный dual-write → переключить чтение → только потом убирать старый путь. Не переписывать исторические данные одним рискованным релизом.

### Правила распределения

1. Входящее сохраняется с provider event id; дубль webhook отбрасывается.
2. По `channel_account + external_chat_id` находится разговор.
3. Контакт связывается отдельно по нормализованному телефону/идентификатору.
4. Если номер есть в ближайшем рейсе — разговор получает ссылку на рейс.
5. Правила могут назначить команду/оператора по каналу, рейсу, ключевым словам или VIP-тегу.
6. Если правило не сработало — «Без оператора».
7. Ответ уходит через канал конкретного разговора, а не просто через последнее входящее по телефону.

## Концепт нового inbox

![Концепт единого inbox](concepts/inbox-v1.png)

Это не финальный дизайн и не предложение немедленно переписать интерфейс. Рендер проверяет логику:

- глобальная навигация стала короче;
- второй столбец — рабочие очереди и канальные фильтры;
- список диалогов всегда показывает канал;
- в шапке разговора видны канал, ответственный и статус;
- справа — рейс, место, автобус, теги и следующие действия;
- composer разделяет ответ пассажиру и внутреннюю заметку.

На ширине меньше 1200 px контекст должен открываться drawer-панелью. На телефоне остаются два последовательных экрана: список → разговор; очереди открываются шторкой.

## Новая информационная архитектура

Рекомендуемый верхний уровень:

1. **Сегодня** — задачи, ошибки, ближайшие рейсы.
2. **Рейсы** — ведомости, пассажиры, документы, подготовка уведомлений.
3. **Входящие** — единый inbox.
4. **Рассылки** — рейсовые и свободные кампании, черновики, история.
5. **Контакты**.
6. **Продажи и отчёты**.
7. **Администрирование** — справочники, каналы, пользователи, диагностика.

На мобильном в нижней панели: `Сегодня · Рейсы · Входящие · Рассылки · Ещё`. Сейчас «Продажи» занимают первичное место, а основной сценарий «Уведомления» спрятан в «Ещё» — для диспетчера это обратный приоритет.

В перспективе карточка рейса должна иметь вкладки `Обзор · Пассажиры · Уведомления · Ответы · Документы`, чтобы оператор не держал в голове связи между четырьмя разделами.

## Что убрать или спрятать

- Блок «Отправить на произвольный номер» со страницы рейсовых уведомлений: перенести в контакт/чат или свободную рассылку.
- Ручную «Проверку каналов» как постоянную основную кнопку: заменить фоновым обновлением и показом «проверено N часов назад».
- «Починить статусы» из обычной поверхности настроек: перенести в admin diagnostics с health-check и журналом результата.
- Дублирование входящих/исходящих в карточке контакта: заменить единой лентой и ссылкой на полноценный разговор.
- Постоянно видимую кнопку удаления рядом с рабочими действиями: перенести в меню и оформить danger-стилем.
- Не убирать: мастер уведомлений, inline-редактирование ведомости, фирменную визуальную систему и печатный экран.

## Техническая стратегия без большого переписывания

### Frontend

Оставить server-rendered PHP и существующий CSS. Для новых интерактивных блоков:

- [htmx](https://github.com/bigskysoftware/htmx) — частичные HTML-обновления, cursor pagination, фильтры и drawer без SPA;
- [Alpine.js](https://github.com/alpinejs/alpine) — локальное состояние dropdown/drawer/фильтров;
- [Chart.js](https://github.com/chartjs/Chart.js) — только для реально полезной динамики продаж/доставки;
- [Lucide](https://github.com/lucide-icons/lucide) — если решите прекратить поддерживать собственный набор SVG.

Не рекомендую сейчас переносить панель на React/Vue и не рекомендую целиком натягивать Tabler/Bootstrap: текущая система уже компактнее и ближе к продукту. DataTables тоже не решит проблему редактируемых сотен строк так хорошо, как серверная пагинация и отдельная форма редактирования.

### Backend

- Ввести Composer, но не превращать проект в framework migration.
- [PHPStan](https://github.com/phpstan/phpstan) — начать с мягкого уровня и поднять его постепенно.
- [Pest](https://github.com/pestphp/pest) или PHPUnit — тесты парсинга ведомости, шаблонов, нормализации телефона, webhook idempotency и routing.
- [Symfony Messenger](https://github.com/symfony/messenger) рассматривать только на этапе устойчивой очереди; сначала допустим простой DB outbox worker.
- [Rector](https://github.com/rectorphp/rector) — позже, для механической модернизации, а не как первый шаг.

Критичнее библиотеки: индексы БД, идемпотентность webhook/send, cursor pagination, outbox, нормальная модель conversation и наблюдаемость.

### Claude Code и агентные библиотеки

- Официальные [Claude Code plugins](https://docs.anthropic.com/en/docs/claude-code/plugins) и [skills](https://docs.anthropic.com/en/docs/claude-code/skills) — базовый формат для собственных проверок проекта.
- [anthropics/skills](https://github.com/anthropics/skills) — официальные примеры структуры skills.
- [obra/superpowers](https://github.com/obra/superpowers) — дисциплина планирования, тестирования и review; брать отдельные подходящие skills, не весь процесс вслепую.
- [wshobson/agents](https://github.com/wshobson/agents) — большой каталог ролей/плагинов для исследования, но сторонние prompts/hooks нужно читать, фиксировать на commit и не давать им production-секреты.

Для этого проекта полезнее создать 4 собственных project skills:

1. `panel-ui-review` — desktop/mobile screenshots, contrast, overflow, keyboard checks.
2. `panel-safe-deploy` — lint, tests, migration check, cache-bust, smoke-test, rollback note.
3. `channel-webhook-contract` — fixtures Evolution/Green API, duplicates, status transitions, media.
4. `manifest-regression` — набор обезличенных CSV разных кодировок и ожидаемый parse result.

## План внедрения

### Этап 0 — 1–2 дня, без изменения продуктовой модели

- Исправить mobile sticky send bar.
- Добавить общий UI ошибок API и восстановление сессии.
- Показать канал в сообщениях чата.
- Сделать дашборд-метрики кликабельными и сравнимыми по периоду.
- Переставить мобильные пункты навигации.
- Убрать произвольный номер из мастера уведомлений.

### Этап 1 — 4–7 дней, inbox foundation

- Добавочные таблицы conversations/events/channel accounts.
- Backfill и dual-write.
- Статусы `new/open/pending/resolved`, assignee, priority.
- Очереди и канальные фильтры.
- Cursor pagination и SQL latest-message query вместо полного UNION + дедупликации в PHP.

### Этап 2 — 4–7 дней, операторская эффективность

- Контекст рейса/пассажира.
- Private notes, шаблоны ответа, вложения.
- Фоновая проверка каналов.
- Поиск по рейсу/сообщениям.
- Перенос карточки контакта на единую activity timeline.

### Этап 3 — 5–10 дней, надёжность отправок

- DB outbox/worker, idempotency keys, retry policy.
- Черновики и планирование рассылок.
- Стоп-лист, дедупликация, кампании и аудит.
- Метрики delivery/read/reply по кампании и каналу.

После каждого этапа: отдельный рендер desktop/mobile → согласование → реализация → smoke-test на обезличенных данных → только затем production.

## Критерии успеха

- Оператор видит все новые ответы без переключения каналов.
- У каждого открытого разговора есть статус и ответственный.
- По сообщению видно его канал и связанный рейс.
- Нельзя случайно отправить одну кампанию дважды.
- Ошибка сети не оставляет экран в бесконечной загрузке.
- На мобильном ни один sticky-элемент не перекрывает форму или навигацию.
- Контакты/логи открываются быстро при 10× текущего объёма.
- Основные действия доступны с клавиатуры и имеют заметный focus.
