## Охват

Read-only проверка стандартных расписаний обнаружила `broadcast_worker.php`
(раз в минуту) и `sales_ingest.php` (раз в пять минут, с прежним отдельным mutex).

других ссылок на приложение не найдено. Это снимок конфигурации, а не доказательство
отсутствия внешнего планировщика или произвольного ручного процесса.

Допуск встроен **до bootstrap** в 12 точек:

Служебные режимы `--dry-run` тоже проходят допуск: некоторые читают почту или
выполняют транзакции с последующим откатом. Допуск не разрешает запуск этих
операций сам по себе. Ограничения AGENTS.md на данные и внешние действия сохраняются.
Старый HTTP-путь `backfill_contacts.php` остаётся в HTTP-контуре; его необходимо
закрывать и дренировать вместе с остальными запросами. Другие перечисленные
скрипты принимают только CLI. Диагностика и автономные тесты не являются заданиями.

## Протокол

`lib/BackgroundJobs.php` не читает конфигурацию приложения, почту или БД.
Каждый исполнитель получает общую shared-блокировку, проверяет состояние и
получает exclusive-блокировку своего имени. Обе удерживаются до конца процесса,
включая shutdown callbacks. Наложение одного задания пропускается; разные задания
могут исполняться одновременно. Автоматического повтора пропущенного запуска нет:
cron повторит его по расписанию, ручной запуск нужно повторить явно.

Состояние по умолчанию находится в `/var/lib/panel-jobs`, вне сменяемого выпуска.
`PANEL_JOBS_STATE_DIR` допускается только как согласованная настройка окружения
CLI; **все** исполнители и контроллер должны видеть один абсолютный канонический
путь на одном локальном файловом разделе. Не помещать состояние в каталог выпуска,
временный каталог, NFS или разные контейнерные файловые пространства.

Каталог создаётся администратором (на сервере — root), режим `0755`, файлы `0644`.
У исполнителя достаточно чтения: Linux `flock` работает на открытом для чтения
дескрипторе. Управление состоянием требует права записи в каталог. Поле `owner` —
идентификатор операции, **не пароль и не замена файловым правам**. Каталог и файлы
не должны быть доступны группе/остальным на запись. Отсутствие, повреждение или
небезопасные права приводят к отказу до бизнес-кода, без автоматического создания.

Lock-файлы создаются один раз. Никогда не удалять, не заменять, не копировать
поверх них и не включать их в переключение релизов: работающий процесс держит
блокировку конкретного inode. При добавлении новых заданий их lock-файлы нужно
отдельно подготовить под закрытым допуском; повторный `init` запрещён.

Контроллер `scripts/jobs_control.php` сериализует команды. `pause` сначала
атомарно сохраняет закрытый допуск и синхронизирует его на диск, затем с ограниченным
временем ждёт exclusive-блокировку всех исполнителей. Уже допущенное задание
заканчивает работу, новые не начинаются. При timeout или остановке контроллера
пауза остаётся. Повтор `pause` с тем же owner позволяет дождаться завершения.

`resume` требует owner текущей паузы и отсутствия активных заданий. Другой
контроллер, устаревший owner или ещё работающий процесс не откроет допуск.
Для каждой новой операции генерировать новый случайный 128-битный owner и сохранять
его в закрытой записи обслуживания; никогда не переиспользовать. Защита дополнительно
отклоняет owner последней завершённой операции, но не ведёт всю историю токенов.
Потеря owner требует сверки текущего состояния администратором, а не удаления каталога.

Подтверждённая пауза синхронизируется вместе с каталогом. При `resume` после
успешного atomic rename нет шага, ошибка которого могла бы вернуть неуспех при
уже открытом допуске. После аварийного выключения неподтверждённая на диске смена
на `running` может вернуться к предыдущей паузе; состояние после перезагрузки нужно
проверить. Реальное выключение питания в тестах не моделировалось.

## Команды оператора

Пример для заранее проверенного выпуска, не инструкция выполнить на production сейчас:

```bash
# Один раз, пока старые расписания остановлены и старые процессы завершились.
operation_id="$(php -r 'echo bin2hex(random_bytes(16));')"
php scripts/jobs_control.php init "$operation_id"
php scripts/jobs_control.php status
# После допуска выпуска и проверок:
php scripts/jobs_control.php resume "$operation_id"

# Следующее обслуживание: новый идентификатор, сохранить до запуска pause.
operation_id="$(php -r 'echo bin2hex(random_bytes(16));')"
php scripts/jobs_control.php pause "$operation_id" 30
# Только код возврата 0 разрешает считать фоновые процессы завершёнными.
# После проверки нового выпуска и разрешения внешних действий:
php scripts/jobs_control.php resume "$operation_id"
```

Коды возврата: `0` — успех; `75` — пауза, занятость, повторный запуск или timeout;
`78` — ошибка настройки, состояния, аргументов или владельца. Не игнорировать
код возврата контроллера. `status` выдаёт только `mode` и `idle`; `idle=true` при
`running` — моментальный снимок, а не разрешение переключать код. Контроллер не
отправляет сигналы рабочим процессам и не сбрасывает очередь.

## Первое подключение и откат

1. Принять PR и собрать полный проверенный `main`. Повторить инвентаризацию всех
   расписаний, пользователей, обёрток и ручных процессов непосредственно перед выпуском.
2. Сохранить расписания. Остановить старые способы запуска, закрыть HTTP и дождаться
   **старых** процессов отдельно: они ещё не знают общей блокировки. Не считать
   `status idle` доказательством отсутствия старых исполнителей.
3. Подготовить постоянный каталог через `init`, оставить paused. Установить полный
   выпуск и проверить одинаковый путь/права под каждой учётной записью. Прежний
   mutex импорта можно сохранить как дополнительную защиту; общая пауза его не заменяет.
4. Проверить схему и приложение через закрытый доступ; затем отдельно разрешить
   возобновление, восстановить расписания и проверить их технические статусы.
   Тесты текущего этапа не выполняют эту установку.
5. При откате на код без guard снова остановить расписания до смены кода и держать
   их остановленными. Старый код не соблюдает состояние paused. HTTP/webhook-допуск
   управляется отдельно по [условиям полного выпуска](qa/full-release-rehearsal.md).

Это барьер обслуживания, не гарантия доставки сообщений, не восстановление
зависших записей очереди и не транзакция между разными видами служебных скриптов.
Принудительное завершение задания может оставить прежние неопределённые результаты;
протокол не делает их безопасными для автоматического повтора. Отделённые дочерние
процессы не допускаются без собственного участия в протоколе. Добавляя планировщик
или CLI-точку записи, включать её в реестр и процессные проверки.

Проверки и ограничения: [процессные тесты](qa/background-jobs.md) и
[общая репетиция полного пакета — 97 утверждений](qa/background-jobs-release-rehearsal.md).
