# Ревью чатов Claude и продолжение inbox-плана

## Что было сделано хорошо

- появился видимый канал последнего сообщения;
- добавлены фильтры WhatsApp/MAX/Telegram/SMS;
- единая карта названий и цветов каналов уменьшила дублирование фронтенда;
- поиск и канальный фильтр корректно совмещались на клиенте.

## Найденные проблемы

### P1 — разные каналы объединялись по телефону

`chat.threads` группировал всё по `phone`. Поэтому WhatsApp и MAX одного пассажира становились одним диалогом, а фильтр показывал только канал последнего сообщения. Это не позволяло надёжно ответить в конкретный канал.

Исправление: разговор теперь имеет ключ `channel + channel_account + external_chat_id`. Телефон остаётся атрибутом контакта, но не идентификатором разговора.

### P1 — прочтение смешивало каналы

`chat.markread` выполнял `UPDATE inbox SET is_read=1 WHERE phone=?`. Открытие WhatsApp помечало прочитанными также MAX/Telegram этого номера.

Исправление: прочтение ограничено сообщениями выбранного `conversation_id`.

### P1 — ответ мог уйти в старый канал

Legacy-функция искала последнее входящее только среди строк с `chat_id`. После нового сообщения WhatsApp она могла выбрать более старый MAX и ответить туда.

Исправление: legacy-путь смотрит последнее входящее независимо от `chat_id`; новый путь отправляет строго через канал и `external_chat_id` разговора.

### P1 — длинный чат показывал старую историю

`ORDER BY ts ASC LIMIT 500` возвращал первые 500 сообщений. Новые сообщения исчезали после достижения лимита.

Исправление: legacy-запрос берёт последние 500; новая модель использует cursor pagination по `(created_at,id)`.

### P2 — список строился полным UNION и дедупликацией в PHP

Каждое обновление загружало всю историю `messages + inbox`. Стоимость запроса росла вместе с базой.

Исправление: денормализованные `last_message_*`, индексы очередей и cursor pagination на 60 разговоров.

### P2 — Telegram-входящие нельзя было отличить от MAX

Green API webhook жёстко записывал `instance=greenapi`, что означало MAX.

Исправление: endpoint поддерживает отдельный `?messenger=telegram`, токен и `instance=greenapi_tg`.

## Реализованное продолжение плана

- additive-таблицы `conversations`, `conversation_messages`, `conversation_events`;
- идемпотентный backfill и dual-write при новых webhook/send событиях;
- очереди: открытые, новые, мои, без оператора, ожидают пассажира, закрытые;
- статус, приоритет, ответственный;
- private notes;
- канальные фильтры по настоящему разговору;
- связь с ближайшим рейсом/пассажиром по телефону;
- пагинация разговоров и сообщений;
- точное прочтение и точный канал ответа.

## Порядок безопасной выкладки

1. Применить `schema15.sql`.
2. Запустить `php scripts/backfill_conversations.php` и сохранить вывод.
3. Сверить количество разговоров и последние сообщения на тестовой копии.
4. Настроить Telegram webhook отдельно:
   `GREENAPI_TG_WEBHOOK_TOKEN=...` и URL `/greenapi-webhook.php?messenger=telegram&token=...`.
5. Выложить код, проверить очереди и ответ в каждом канале на тестовых контактах.
6. Старые `messages/inbox` не удалять: dual-write остаётся страховкой до отдельного этапа переключения.
