# Повторная доставка входящих сообщений

Задача #46, RULE-06/07/11/15, RISK-005/006/008/013/014. Реализация требует
`schema30.sql`. Применение к рабочей БД и выпуск выполняются отдельно после допуска.

## Контракт

Green API: идентичность сообщения определяется провайдером, настроенным
idInstance, каналом, chatId и idMessage. idInstance из события обязан совпасть
с настройкой соответствующего канала. Поддерживаются MAX, Telegram, WhatsApp.
Evolution: ключ содержит провайдера, зарегистрированный instance, WhatsApp,
remoteJid и key.id. Регистрация проверяется по wa_accounts/provider=evolution;
активность для исходящих отправок не запрещает принять входящее от другого
зарегистрированного аккаунта. Пакет проверяется полностью до первой записи.

Состав ключа версионирован, сериализуется однозначно и хешируется SHA-256. Текст,
имя и время доставки не участвуют: два разных сообщения с одинаковым текстом
сохраняются отдельно. Для повтора действует результат первой принятой версии.
Данный механизм не является реализацией редактирования или удаления сообщений.

В одной транзакции InnoDB создаются уникальная отметка приёма, inbox, запись
диалога, счётчик непрочитанных и изменение подписки STOP/START. Конкурирующий
повтор ждёт исход транзакции. При успешном исходе повтор не изменяет состояние;
при ошибке повтор может выполнить всё заново. Ошибки диалога/подписки больше
не скрываются как успешный приём. Нет схемы или запись не завершилась — HTTP 503,
не 200. Неверные входы получают 400, неверный секрет — 403, без бизнес-записей.

Группы и неподдерживаемые типы содержимого игнорируются по прежней политике;
добавлено распознавание групп MAX по chatType. Входящий обработчик требует корректную структуру и устойчивый идентификатор;
ошибочная структура не считается успешно обработанным сообщением. Новые delivered/read обрабатываются отдельно
от дедупликации входящих сообщений. Существующие обработчики исходящих статусов
не переделаны в устойчивую очередь; их конкурентная материализация — отдельный риск.

Источники: [формат Green API MAX](https://green-api.com/v3/docs/api/receiving/notifications-format/incoming-message/TextMessage/),
[отправка](https://green-api.com/v3/docs/api/sending/SendMessage/),
[статусы](https://green-api.com/v3/docs/api/receiving/notifications-format/statuses/OutgoingMessageStatus/).
Поведение подтверждено тестовыми событиями; живые очереди и внешняя доставка
не использовались. Для Evolution сохранён поддерживаемый репозиторием формат.

## Вложения и автоответы

Вложение загружается только владельцем транзакции. Полный файл публикуется
атомарным переименованием в `<хеш события>.bin` в закрытом хранилище и выдаётся
существующим авторизованным контроллером. После отката БД файл может остаться:
повтор использует ту же копию. Неудачная загрузка не подтверждает событие.
Аварийно оставшиеся временные файлы могут потребовать отдельной согласованной
очистки. Новая реализация не обещает атомарность файловой системы и БД.

Автоответ сохраняется со снимком текста и состоянием `pending` вместе с входящим.
После commit один исполнитель атомарно меняет его на `unknown` **до** обращения
к провайдеру. Повтор может продолжить `pending`, но никогда автоматически
не повторяет `unknown` или `accepted`. Подтверждённое принятие провайдером
сохраняется вместе с исходящим сообщением/диалогом как `accepted`.

Это не более одной попытки вызова провайдера. Авария после фиксации попытки,
таймаут или отказ записи после внешнего приёма могут оставить автоответ
неотправленным либо принятым без локального подтверждения. Основное входящее
сообщение и подписка уже сохранены. `accepted` не означает доставку.

Контроль оператора — `php scripts/incoming_status.php`: состояния, количество
и возраст, без содержимого переписки. Зависшие `pending` и `unknown` требуют
сверки с провайдером; не переводить их массово в pending и не повторять отправку
на основании одного таймаута. Нового фонового отправителя нет. Рабочая отправка
и сверка с реальным провайдером требуют отдельного согласия.

## Preflight, применение и откат

1. Сохранить согласованную копию БД, кода и закрытых файлов; проверить восстановление.
2. Сверить точный commit и существующую схему. Нужны актуальные inbox/contacts,
   conversations/conversation_messages, messages и их зависимости. Все таблицы
   записываемой транзакции должны быть InnoDB. Не применять диапазон старых схем.
3. Отдельно согласовать `schema30.sql`, закрыть приём новых запросов и дождаться
   завершения принятых. Скрипт создаёт только incoming_receipts; существующие
   сообщения не переписываются и не объединяются. CREATE IF NOT EXISTS допускает
   повтор, но не исправляет ранее созданную таблицу неправильной структуры.
4. Выполнить `php scripts/check_incoming_schema.php`. Он проверяет движки,
   обязательные колонки, типы и первичный ключ отметок. Это необходимая, но не
   полная проверка всей схемы/версий: дополнительно профильные тесты.
5. Проверить наличие ID для каждого настроенного Green API канала и регистрацию
   Evolution instance. Секреты в отчёт не выводить. Старые события без устойчивого
   ID не объединять по тексту; решить совместимость до снятия паузы.
6. Выпускать полное проверенное дерево main по общему порядку. Закрытый тест
   приёма/повтора/ошибки должен пройти до открытия доступа.

Откат к старому коду не требует удаления добавочной таблицы и не должен заменять
текущую БД старым дампом. Но старый обработчик снова допускает повторы, поэтому
при возврате старого кода входящие webhook должны оставаться на безопасной паузе,
пока не восстановлен защищённый приём. Таблицу отметок сохранять: её удаление
разрешило бы повторную обработку уже принятых событий. Сам по себе откат кода
не сохраняет новую гарантию обработки. Учитывать срок очереди провайдера.

Нет автоматического удаления отметок: согласовать срок хранения отдельно от
срока webhook-очереди. Объём таблицы контролировать. Исторические сообщения без
отметок не защищены от очень позднего повтора старого события; автоматический
backfill по тексту/телефону запрещён.

## Воспроизведение проверок

- `./scripts/preflight.sh` включает локальные проверки нормализации, идентичности,
  транзакций/отката и переиспользования файла; SQLite не доказывает блокировки InnoDB.
- `tests/incoming_webhooks_mysql_test.php` использует реальный bootstrap и отдельную
  MariaDB в закрытом сетевом пространстве. Требует `INCOMING_TEST_ACK=isolated-copy`
  и `INCOMING_TEST_DATADIR`, совпадающего с фактическим datadir. Записывает только
  искусственные объекты, создаёт временные триггеры для моделирования отказа.
  Не запускать на рабочем серверном окружении/БД.
- Отдельная HTTP-репетиция использует настоящие nginx/FPM/обработчики и искусственные
  события. Скрипты окружения и результаты сохраняются в закрытом приложении;
  опубликованный отчёт — [qa/incoming-events.md](qa/incoming-events.md).
