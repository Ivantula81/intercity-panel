# Репетиция переключения полного выпуска

05.10.2026, Europe/Belgrade. Журнал #35, подготовка #42, восстановление #44,
исправление повторов [#46](https://github.com/Ivantula81/intercity-panel/issues/46).
RULE-01/06/07/11/15; RISK-001/003/006/008/013/014.

**Результат:** 31 проверенное утверждение о переключении и откате успешно;
отдельная проверка однократной обработки входящего события не пройдена.
Выпуск **не готов и не выполнен**. Количество утверждений не означает
31 независимый пользовательский сценарий.

## Версии и изоляция

Предыдущий полный код: `02f31c2ae0fa08f5ae418aaa3e7003ad27a2d38e`.
Кандидат: `ea4bdda561c05de5353495dcd879130a69d85fc7`.
Использованы полные деревья Git и ранее восстановленные копии БД и файлов.
Оба дерева обращались к одним скопированным рабочим хранилищам.

Отдельные nginx/FPM работали в изолированных сетевом и файловом окружениях.
До записывающих тестов подтверждены отсутствие внешнего сетевого интерфейса
и фактический каталог подключённой тестовой БД. Секреты тестовые, входящие
события искусственные; исходящие сообщения не отправлялись.
Действующие каналы, расписания, веб-сервер и путь рабочего сайта не переключались.
Скрипты и технические результаты сохранены в закрытом приложении; копии данных,
секреты, реальные сообщения и эксплуатационные настройки в Git не включены.

## Проверенное поведение

| Этап | Подтверждение |
| --- | --- |
| Исходный выпуск | Ответ PHP и ресурсы JS/CSS соответствуют предыдущему коду, OPcache включён, страница входа доступна. |
| Начало паузы | Новые запросы получают 503 и Retry-After; входящее событие не подтверждается и не записывается. |
| Завершение операций | Уже принятый медленный запрос заканчивается с 200 на старом коде; модель фонового задания завершает работу, новое задание не стартует. |
| Первое переключение | Пауза скрывает промежуток при переносе обычного каталога; ссылка атомарно меняется на полное дерево кандидата. |
| Запуск кандидата | Пауза сохраняется до доступности сокета нового FPM; после открытия проверены хеши PHP/JS/CSS, OPcache и страница входа. |
| Входящие после паузы | Повтор отклонённого во время паузы искусственного события принимается и создаёт одну запись. |
| Возврат кода | Предыдущие PHP/JS/CSS восстановлены, новые синтетические запись и файл сохранены, модель задания снова запускается. |

Для JS проверено изменение временного маркера версии ресурса. Это HTTP-проверки,
браузерный кэш и JavaScript здесь не исполнялись. Отдельные проверки браузерного
восстановления описаны в [workspace-restore.md](workspace-restore.md).

## Исправление процедуры завершения запросов

В первой попытке сигнал плавного завершения FPM не сохранил принятый медленный
запрос: nginx получил разрыв соединения, клиент — ошибку. Процедура изменена:
сначала закрыть допуск, дождаться завершения фонового задания и нулевой активности
с пустой очередью FPM, проверить ответ принятого запроса, затем остановить FPM.
Повтор с этой последовательностью прошёл.

Контроль FPM использовал отдельный закрытый status socket, доступный при занятых
рабочих процессах. Возможность независимого status pool описана в
[настройках PHP-FPM](https://www.php.net/manual/en/install.fpm.configuration.php),
смысл активности и очереди — в [описании статуса FPM](https://www.php.net/fpm.status.php).
Измеренные 2,411 секунды относятся к искусственному медленному запросу и модели
задания; это не оценка простоя рабочего сайта.

## Повторная доставка: отрицательный результат

Повтор того же искусственного входящего события после успешного приёма дал
вторую запись вместо сохранения одной. Так моделируется потеря подтверждения:
отправитель вправе повторить событие, которое приложение уже сохранило.
Это подтверждает RISK-014 в изолированной копии; наличие дублей в рабочих
переписках не исследовалось. Задача #46 задаёт критерии исправления, включая
конкурентные повторы, сбои сохранения и различение новых статусов.

По [контракту GREEN-API для MAX](https://green-api.com/v3/docs/api/receiving/technology-webhook-endpoint/)
повторы выполняются с минутным интервалом, срок хранения уведомления ограничен
24 часами. [Общие рекомендации GREEN-API для WhatsApp](https://green-api.com/docs/api/recommendations/working-with-incomming-webhooks/)
связывают удаление уведомления из очереди с ответом 200. Контракты разных каналов
не считать взаимозаменяемыми. Реальная очередь и длительная недоступность
провайдера не проверялись; Retry-After сам по себе не гарантирует повтор.
Проверка входящей доставки не разрешает слепой повтор исходящих отправок.

## Ограничения и оставшиеся условия

- Фоновая работа проверена синтетическим исполнителем с общей блокировкой.
  Реальные задания не запускались и ещё не приведены к этому протоколу.
- До снятия паузы проверялась доступность сокета FPM. Полная проверка кандидата
  через закрытый канал до допуска пользователей остаётся частью подготовки.
- Откат проверен без активного медленного запроса и реального фонового задания;
  протокол завершения операций при откате под нагрузкой ещё требует проверки.
- Искусственное входящее событие не содержало вложений и не запускало внешних
  действий. Другие типы событий и провайдеры требуют профильных тестов.
- Сценарий защиты от повторов должен пройти после исправления #46. Общая
  блокировка и безопасная пауза должны охватить все действующие исполнители.
- Исторические стоп-условия, включая серверные права ролей, остаются обязательны.
  Репетиция не подтверждает защиту от потери всего сервера.

После завершения тестовая БД остановлена, изолированных nginx/FPM/исполнителей
не осталось. Повторная сверка подтвердила совпадение 208 рабочих файлов с
`02f31c2`, HTTPS-страница входа доступна, рабочие службы активны. Изменение
настроек сессий относится к [предыдущему этапу](recovery-rehearsal.md);
в этой репетиции рабочий код и настройки не менялись. #42/#44 остаются открытыми.
