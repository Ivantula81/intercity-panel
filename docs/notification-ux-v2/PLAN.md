# Уведомления v2 — UX-аудит и план

## Короткий вывод

Текущий раздел функционален, но оператор вынужден вручную управлять техническими этапами: раскрывать каждую из 15 групп, проверять получателей и каналы, отправлять, затем снова раскрывать группу для статусов и вручную выбирать запасной мессенджер. Это увеличивает риск пропустить пассажира и не даёт простого ответа на главный вопрос: «все ли получили актуальную информацию?»

Предлагаемый принцип: **система сама готовит и доставляет, оператор подтверждает содержание и разбирает только исключения**.

Интерактивный рендер: `notification-center-v2.html`. Переключатель сверху показывает состояния «Подготовка» и «Доставка».

## Что неудобно сейчас

1. «Проверить каналы» повторяется внутри каждой группы, хотя проверять нужно всех пассажиров ведомости одним фоновым действием.
2. Проверка получателей спрятана внутри 15 карточек; нет общего списка ошибок и дублей.
3. Кнопка «Отправить все группы» не показывает готовность данных: сколько уйдёт, сколько не уйдёт и почему.
4. Статусы доставки спрятаны внутри каждой группы и загружаются только после раскрытия.
5. Запасной канал выбирается вручную для каждого пассажира.
6. «Журнал доставки» смешивает разные рейсы и технические попытки; оператору важен итог по текущей ведомости.
7. Ответы пассажиров дублируют назначение раздела «Чаты» и визуально удлиняют экран.
8. Повторные клики и повторная отправка требуют строгой защиты от дублей; сейчас интерфейс не объясняет, кому сообщение уже отправлялось.
9. Термины отражают устройство системы («каналы», «проверка», «статусы»), а не задачу оператора («готово», «получили», «нужно действие»).

## Предлагаемый сценарий

### 1. После загрузки — автоматическая подготовка

Один фоновый процесс выполняет:

- проверку номера и поиск дублей;
- сверку времени и адреса посадки;
- проверку доступных каналов для всех телефонов;
- создание групп «откуда → куда»;
- формирование и проверку текстов;
- расчёт готовых и проблемных получателей.

Оператор видит не кнопки этих операций, а чек-лист результатов и одну очередь исключений.

### 2. Подтверждение перед отправкой

На одном экране:

- сколько пассажиров и направлений;
- сколько получат через основной канал;
- сколько переключатся на запасной канал;
- кто требует ручной правки;
- группировка по городу отправления;
- общий текст и время на город отправления, точечное переопределение для направления.

Главная кнопка должна называться конкретно: «Отправить 39 пассажирам», а не «Отправить все группы».

### 3. Автоматическая доставка

Настраиваемая политика, например:

`WhatsApp → MAX → Telegram → SMS`

Переход на следующий канал выполняется только когда:

- подтверждено отсутствие аккаунта в основном канале;
- отправка завершилась явной постоянной ошибкой;
- либо истёк заданный срок ожидания, если это разрешено настройкой.

Временные ошибки сначала повторяются в том же канале. Каждая логическая отправка имеет ключ идемпотентности, поэтому повтор кнопки или перезапуск worker не создаёт дубль.

### 4. Экран результата

Вместо 15 отдельных раскрываемых мониторов:

- прочитали;
- доставлено;
- отправлено, ждём подтверждения;
- требуется другой канал;
- требуется ручное действие.

Основная рабочая кнопка: «Доставить оставшимся N». Система уже предлагает подходящий канал. Ручная отправка по одному остаётся только запасным действием.

Ответы пассажиров показываются счётчиком и ссылкой «Открыть 3 ответа в чатах», а не длинной лентой внизу уведомлений.

## Что оставить

- точное разделение групп «откуда → куда»;
- сортировку блоками по отправлению;
- редактирование телефона и пассажира;
- отдельный текст для конкретного направления;
- ручной выбор канала как аварийный вариант;
- предпросмотр сообщения;
- отметки «прочитано» и «доставлено».

## Что убрать с основного экрана

- кнопку «Проверить каналы» в каждой группе;
- отдельную кнопку «Статусы доставки» в каждой группе;
- постоянную кнопку «Сбросить к шаблону» в каждой карточке — перенести в меню;
- длинный общий журнал всех рейсов;
- длинную ленту ответов пассажиров;
- 15 одновременно доступных кнопок «Отправить этой группе» — оставить внутри деталей как дополнительное действие.

## План реализации

### Этап 1 — новый экран без изменения отправки

- добавить агрегированную готовность ведомости;
- собрать проблемы телефонов, времени, адресов и шаблонов в единую очередь;
- автоматически проверять каналы пакетами после загрузки;
- показать компактные направления блоками по отправлению;
- сделать единый монитор доставки по текущей ведомости;
- ответы перенести ссылкой в «Чаты».

Риск низкий: отправка остаётся существующей, меняется представление и подготовка.

### Этап 2 — безопасная серверная кампания

- сущность `notification_campaigns`;
- логическая доставка на пассажира `notification_deliveries`;
- попытки по каналам `notification_attempts`;
- уникальный idempotency key на «рейс + пассажир + версия текста»;
- фоновая очередь и повтор временных ошибок;
- единый API подготовки, запуска и статуса кампании.

Без этого автоматический fallback может создавать дубли и не должен включаться.

### Этап 3 — автоматический выбор запасного канала

- настраиваемый порядок каналов;
- правила постоянной и временной ошибки;
- срок ожидания подтверждения доставки;
- массовая кнопка «Доставить оставшимся»;
- аудит: кто, когда и почему переключил канал.

### Этап 4 — эксплуатация

- уведомление оператору, если остались недоставленные;
- фильтр «требует действия» на дашборде;
- метрики доставки по каналам;
- шаблоны правил для разных типов уведомлений;
- сценарии тестирования на реальной ведомости без фактической отправки.

## Решения, которые нужно согласовать перед кодом

1. Допустимо ли автоматически переходить с WhatsApp на MAX/Telegram или оператор всегда подтверждает массовый fallback?
2. SMS использовать автоматически только для срочных уведомлений или всегда последним каналом?
3. Что считать успехом: API принял сообщение, сообщение доставлено или прочитано?
4. Через сколько минут без доставки предлагать другой канал?
5. Должен ли пассажир получить сообщение только один раз, если оно уже доставлено в любом канале? Рекомендация: да.

## Рекомендуемый первый релиз

Сначала реализовать Этап 1 и серверную идемпотентность из Этапа 2. Автоматический переход между каналами включать только после накопления статистики ошибок. В первом релизе система сама проверяет и предлагает запасной канал, а оператор подтверждает одной кнопкой всех оставшихся пассажиров.
